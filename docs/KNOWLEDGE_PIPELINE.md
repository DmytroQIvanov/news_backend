# База знань: збір, зв'язки, події, факти

Основа проєкту — не тексти статей, а **граф знань**, який наповнюють алгоритми: документи → згадки сутностей → події →
твердження → факти → зв'язки між подіями. LLM (Gemini) бере з цієї бази готовий, перевірений, стиснений «досьє»
і пише текст. Саме ця база дає те, чого людина не отримає «зі свого ШІ»: історію, яку модель не пам'ятає,
крос-перевірку десятків джерел і причинно-наслідкові ланцюжки з датами.

```
RSS · сайти · API · офіційні заяви · документи · датасети (задача 3)
        │  kb-collector: feedparser + httpx (ETag/304), trafilatura, AMP-фолбек, robots.txt, перевірка змін
        ▼
kb.documents ──────────────── stage: new → extracted → analyzed → clustered
        │  kb-nlp (без ШІ): дублікати (SHA-256, SimHash) · мова (lingua) · spaCy NER + синтаксис ·
        │  словник сутностей + Wikidata · YAKE · ембеддинги (fastembed) · категорія (правила → модель → ембеддинг) ·
        │  твердження (правила над синтаксисом: хто/що/кому/скільки/коли/хто каже)
        ▼
kb.events (кластери-сюжети) · kb.claims → kb.facts (+ kb.contradictions) · kb.entity_relations
        │  kb-maintain: Wikidata-резолюція нових імен · статистика · NPMI-зв'язки ·
        │  сюжетні лінії, прецеденти, реакції (kb.event_links) · навчання класифікатора
        ▼
kb.llm_tasks — бюджетована черга для Gemini: лише нові факти, суперечності, складні/причинні зв'язки, підсумки змін
        ▼
NestJS API / редакційний конвеєр (задачі 1 і 4)
```

## Розгортання на окремому сервері

```bash
git clone <repo> && cd opportunity-radar-starter
cp .env.server.example .env.server && chmod 600 .env.server   # заповнити паролі та ключі
docker compose -f compose.server.yaml --env-file .env.server up -d --build
docker compose -f compose.server.yaml --env-file .env.server run --rm kb-maintain seed
docker compose -f compose.server.yaml --env-file .env.server run --rm kb-maintain backfill --fetch-days 7
docker compose -f compose.server.yaml --env-file .env.server run --rm kb-maintain stats
```

Контейнери: `db` (PostgreSQL 17 + pgvector), `migrate` (одноразово), `api` (NestJS), `kb-collector`, `kb-nlp`,
`kb-maintain` (один образ, різні команди), `backup` (щоденний `pg_dump`, 14 днів), `caddy` (HTTPS, профіль `proxy`).
Масштабування аналізу: `--scale kb-nlp=3` — рядки орендуються через `SKIP LOCKED`, репліки не конфліктують.

### Кращі практики для сервера
- **Розмір на старт:** 4 vCPU, 8–16 ГБ RAM, 100+ ГБ NVMe. `kb-nlp` ≈ 1,5–2,5 ГБ RAM (spaCy + ONNX-модель).
- **Безпека:** SSH лише за ключем, `ufw allow 22,80,443`, Postgres слухає тільки `127.0.0.1` (адмінка через SSH-тунель),
  контейнери без root, секрети тільки в `.env.server` (600), `unattended-upgrades`.
- **Бекапи:** локальні дампи + **поза сервером** (restic/rclone у Cloudflare R2 або Backblaze B2, у вас вже є R2).
  Раз на місяць — тестове відновлення в окремий контейнер.
- **Моніторинг:** `kb.pipeline_runs` (кожна ітерація воркера зі статистикою), `python -m kb stats`; далі Uptime Kuma
  для `/health`, pgHero або `pg_stat_statements` для повільних запитів, Grafana — коли з'явиться потреба.
- **Оновлення:** збірка образів у GitHub Actions → GHCR, на сервері `docker compose pull && up -d` (без збірки на проді).
- **Ріст даних:** до ~10 млн документів PostgreSQL достатньо; далі — партиціювання `kb.documents`/`kb.mentions` за місяцем
  і архів тіл статей у R2.

## Перевірено на живих даних (17 листопада 2026)

Тестова PostgreSQL 17 (без pgvector, тобто **без семантичного сигналу** — на сервері він буде), 17 джерел UA/EN:
383 нові статті → 285 повних текстів (59 коротких повних новин), 33 часткових, 13 тизерів, 42 заблоковано;
аналіз 373 документів за 81 с на CPU (≈4,6 док/с з ембеддингами). 16 подій у стані `ready`, переважно справжні
багатоджерельні сюжети: позов Каліфорнії до OpenAI (4 незалежні видання), атака на Кримський міст (BBC + Guardian),
«Рамштайн»/F-16 (УП + Суспільне), Швеція 65 млн € (УП + Суспільне, різні округлення суми), дрони над Молдовою.
Знайдено й виправлено за реальними даними: хибні збіги словника («мали»→Малі, «того»→Того, «дія»→Дія), «підвали»
статей із закликами підписатися, «Telegram» як канал заяви → помилкова категорія, склеювання різних подій через
загальні сутності («Україна», «США») — тепер IDF-специфічність і «маса спільних доказів».
Відомі обмеження до сервера з pgvector: кілька кластерів одного джерела (блог NVIDIA, BleepingComputer) ще
склеюються за ім'ям компанії; на сервері це відсікає семантична схожість.

Незалежне рев'ю коду від Codex знайшло 22 потенційні проблеми (гонки між репліками, ідемпотентність, крайові
випадки фактів) — виправлено ключові: відновлювані стадії черги й продовження оренди, advisory-lock на кластеризацію
й агрегацію фактів, злиття подій із перерахунком центроїда, заперечення («спростував, що купив») ніколи не стає
фактом, граф відносин перебудовується з фактів (без плюсів від «не купив»/«планує»), сума порівнюється лише в тій
самій валюті й близьких датах, одна підтримка maintenance на весь кластер.

## Наскрізні вимоги (враховуються в усіх задачах)

**Бюджети LLM.** Gemini 3.8 Flash, 3.6 Flash і 2.5 Flash — по **20 запитів на день** кожна, Hydrogen — до 20.
Вхід до 250 тис. токенів на запит, тому кожен виклик має бути «щільним»:
- **пакетування задач:** один виклик перевіряє 30–60 фактів, розв'язує 20–40 неоднозначних сутностей або пояснює
  10–20 суперечностей (черга `kb.llm_tasks` групується за `task_type`, відповідь — JSON-масив з ID задач);
- **одна велика стаття — один виклик** з повним досьє (60–150 тис. токенів) або **кілька статей за виклик**
  (3–5 подій `ready` з компактними досьє, кожна стаття окремим об'єктом у JSON);
- розподіл (стартова пропозиція): 3.8 Flash — великі статті (20 × 1–2 = 20–40/день); 3.6 Flash — оновлення
  статей новими доказами, переклади, зведення змін пакетами; 2.5 Flash — пакетна перевірка фактів, сутностей,
  суперечностей; Hydrogen — план/кут/причинний аналіз і фінальна критика флагманів (5–10 × 2);
- **атомарний облік** у БД (`llm_budget_days`, резервування перед кожною HTTP-спробою, включно з повтором) —
  спільний для NestJS і Python, щоб жоден процес не перевищив ліміт; поточний лічильник у пам'яті NestJS
  (`gemini-client.ts`, 150/день за замовчуванням) замінюється ним;
- кешування: досьє та його хеш зберігаються; якщо доказів не додалося — повторна генерація не запускається.

**Зв'язки — у застосунок і в генерацію.** Те, що будує база (події, сюжетні лінії, прецеденти, реакції, факти зі
статусами, профілі сутностей), має бути видно читачеві й використано ШІ:
- API NestJS: `/kb/events/:id` (джерела, хронологія, пов'язані події, факти зі статусами, суперечності),
  `/kb/entities/:id` (профіль, зв'язки, хронологія), `/kb/storylines/:id`;
- застосунок: екрани «Сюжет», «Хронологія», «Що було раніше», картки людей і організацій, позначка
  «підтверджено N незалежними джерелами»;
- генерація: досьє містить ці зв'язки з ID, текст посилається на них, валідатор перевіряє кожне посилання.

**Відео та аудіо як джерела.** Спочатку готові субтитри (майже без CPU), далі — лише звук через FFmpeg
(моно, 16 кГц, Opus ~24 кбіт/с), VAD (WebRTC VAD — найлегший; Silero VAD у ONNX — точніший), вирізання довгих пауз,
прискорення 1,1–1,25× (перевіряти якість), транскрипція через Gemini з картою відповідності таймкодів до оригіналу;
whisper.cpp `base` — запасний варіант при вичерпаній квоті (повільно на малому CPU). Транскрипт стає
`kb.documents` (kind `transcript`) і проходить **той самий алгоритмічний конвеєр** — твердження, сутності, події
без LLM; Flash-Lite аналізує текст лише один раз, результат зберігається в базі.

## Задачі далі

### Задача 2b — надійність бази (зроблено 17.11.2026)
- **Черга:** оренда з токеном власника (`lease_token`); кожен запис перевіряє власника, тож воркер із простроченою
  орендою не може перезаписати чужий результат; `analyzer_version` + `maintain.requeue_outdated()` повторно
  аналізують документи після зміни коду.
- **Корені доказів** (`kb/nlp/attribution.py`, `resources/outlets.yaml`): «за даними Reuters», «– Reuters» у
  заголовку, «Reuters:», «citing Bloomberg» → корінь = Reuters. Два видання, що переказують Reuters, — одне
  підтвердження. Тизери й передруки не підтверджують. Першоджерело підтверджує лише факти про себе
  (`speaks_for_entity_id`: блог NVIDIA → NVIDIA).
- **Факти:** тривалі (купив, призначив, захопив) зливаються між подіями, епізодичні (удар, допомога, зустріч) —
  окремий факт на кожну подію; суми — в `kb.fact_values` з історією й коренями; «уточнення» (той самий корінь або
  зростаючий підрахунок жертв) ≠ суперечність; суперечність лише коли незалежні корені розходяться >15% у тій самій
  одиниці; суперечність автоматично закривається, коли нові докази її пояснюють.
- **Твердження:** сума, дата, модальність і заперечення беруться з **підрядного речення самої дії**
  («A інвестувала 10 млн, B планує 50 млн» → кожному своє); майбутній час доконаного виду («придбає») = план;
  «Компанія заявила…»/«It will…» → попередній названий актор; підмет «намір підписати», «запровадила санкції» —
  від керівного дієслова; «засудив … до 8 років» = вирок, «засудив напад» = осуд; «повідомили про підозру» =
  обвинувачення; «пообіцяла» ≠ «передала»; торгівля ≠ допомога; «заперечив придбання X» = заперечене придбання;
  «за словами X» = атрибутована заява; місце дії («у Берліні») не стає об'єктом; зброя/продукт не можуть бути
  суб'єктом фінансових дій.
- **Вимірювання:** `knowledge/eval/gold_claims.yaml` (83 твердження, uk/en/de, усі «пастки») і
  `python -m kb eval [--failures]`. Було → стало: точність 0,77 → **0,96**, повнота 0,68 → **0,90**, F1 0,72 → **0,93**,
  модальність 0,93 → **0,99**, заперечення й дати 1,00. Поріг якості — у тестах і CI. Найслабше — німецька
  (мала модель spaCy): для неї варто `de_core_news_md/lg`.
- **Ще відкрито з порад Codex:** many-to-many «документ ↔ подія» для оглядів; «подієві фрейми» (місце + час
  події) для ударів; контекстне розв'язання тезок; розширення еталону до ~500 документів із реальних статей.

## Video worker (migration 033, container kb-video)

Backend with `KB_VIDEO_WORKER=true` queues worthy YouTube videos (`youtube_videos.status = queued_kb`) instead of calling Gemini. `python -m kb video`:
1. uploaded subtitles → automatic captions (yt-dlp, no LLM);
2. else yt-dlp audio → FFmpeg 16 kHz → WebRTC VAD drops pauses > KB_VIDEO_MAX_PAUSE → atempo KB_VIDEO_SPEED → Opus 24k → Gemini Flash-Lite transcription; a time map restores ORIGINAL timecodes; whisper.cpp base (built into the image) on any failure;
3. transcript → kb.documents kind `transcript` ("[mm:ss] text"), analysed by the algorithmic NLP pipeline like any document;
4. one Flash-Lite analysis → radar fields (title/summary/takeaways/quotes) + kb.video_claims (statements with timecodes, speaker linked to entities). Never analysed twice; waits for budget without re-transcribing.

Flash-Lite is outside the 20/day limits; budgeted models still go through llm_budget_days. YouTube may challenge datacenter IPs: set KB_YTDLP_PROXY if subtitles/audio downloads fail.
