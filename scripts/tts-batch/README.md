# Пакетний TTS: окремий експеримент

Мета: один TTS-запит → 2 новини × 3 режими → 6 кандидатів на аудіофайли.
Без транскрипції, ffmpeg, додаткових npm-пакетів та запису в бойовий кеш озвучок.
Працює окремим Node.js-процесом у тому самому середовищі, що й API.

## Запуск на сервері

Потрібні Node 22, `npm ci`, актуальний `npm run build`, серверні `GEMINI_API_KEY`
і `DATABASE_URL`. Ключ не передавати аргументом командного рядка. Скрипт читає
змінні середовища та кореневий `.env`. Всі шляхи нижче — від кореня backend.

Спершу підготувати сценарій із двох останніх опублікованих новин (0 TTS-запитів):

```sh
node scripts/tts-batch-lab.cjs --from-db --out /persistent/tts-lab/preview
```

Прочитати `transcript.txt`. Реальний запуск, рівно одна HTTP-спроба, без повторів
і без переходу на іншу модель:

```sh
node scripts/tts-batch-lab.cjs --run /persistent/tts-lab/preview --generate
```

`--run` використовує саме підготовлені тексти, а не повторно вибирає новини.
Для прикладів нижче каталог запуску названо `preview`.
`/persistent/tts-lab` замінити на доступний для запису каталог постійного диска.
За замовчуванням результати пишуться в `backups/tts-batch-lab/<UTC timestamp>`.
На Render без постійного диска файли зникнуть при перезапуску/розгортанні:
скопіювати весь каталог результату на комп'ютер до цього моменту.
Не потрібен постійний worker: процес завершується після отримання й аналізу.
Немає таймера, cron або генерації вночі.

Для контрольного прикладу: `--input scripts/tts-batch/example.json` замість
`--from-db`. Це явно вигадані новини. Для пакета з трьох озвучок передати одну
статтю. Можна передати готові тексти у форматі
`{"segments":[{"id":"news-1/short","text":"..."}, ...]}`: рівно 3 або 6 елементів.

Модель за замовчуванням: `gemini-3.8-flash-tts`; дозволена також
`--model gemini-3.8-flash-lite-tts`. Не підміняємо їх старими моделями, бо формат
пауз залежить від моделі. Між фрагментами додається тільки `<long pause>`, без
службових фраз. Формат: [офіційна документація Gemini](https://ai.google.dev/gemini-api/docs/speech-generation).
Голос `Kore`, можна задати `--voice NAME`.

## Як розрізається звук

- WAV PCM16 mono/stereo, максимум 10 хвилин / 64 MiB. Збереження оригіналу перед аналізом.
- RMS і пікова гучність у вікнах 20 мс. Початкові пороги: RMS −42 dBFS,
  peak −30 dBFS, тиша від 1.2 секунди. Розмір даних і час аналізу лінійні.
- Вступна/кінцева тиша не вважаються внутрішніми межами.
- Потрібно рівно 5 внутрішніх довгих пауз для 6 текстів або 2 для 3 текстів.
  За іншої кількості жодного автоматичного зрізу не створюємо.
- Перевіряємо мінімальну тривалість і грубу відповідність довжинам текстів.
  На кожному краї біля паузи залишаємо 150 мс; внутрішня тиша забирається.
- Навіть правильна кількість пауз не доводить правильність меж. Статус завжди
  `candidate_cuts_need_listening` або `manual_boundaries_required`, ніколи «перевірено».

Якщо модель озвучить тег, пропустить текст або зробить довгу паузу всередині
новини, цей аналіз не може гарантовано це виявити. Потрібне прослуховування.
За невдалого розрізання нового TTS-запиту автоматично не буде.

## Повторний аналіз без витрат Gemini

```sh
node scripts/tts-batch-lab.cjs --analyze /persistent/tts-lab/preview --threshold-db=-46 --min-silence 0.9
```

Кожен аналіз створює власну папку `analysis-*`: `index.html`, `report.json`,
посилання на `original.wav` і, якщо межі однозначні за евристикою, `01.wav`…`06.wav`.
Графік гучності, всі паузи, тексти й часові межі доступні у звіті.
Оригінал повторно не копіюється: використовується hard link на тому самому диску.
Не видаляти оригінал або report до завершення оцінювання.

Для прослуховування запустити на сервері:

```sh
node scripts/tts-batch-lab.cjs --serve /persistent/tts-lab/preview/analysis-TIMESTAMP --port 8791
```

На комп'ютері відкрити SSH-тунель `ssh -L 8791:127.0.0.1:8791 USER@HOST`
і перейти на `http://127.0.0.1:8791`. Сервер слухає тільки loopback.
Альтернатива: скопіювати папку аналізу з розіменуванням hard link і відкрити
через локальний HTTP-сервер. У програвачі можна змінити початок/кінець кожного
фрагмента й завантажити ручний WAV-зріз: усе виконується в браузері, без API.
Ручні межі не зберігаються після перезавантаження сторінки.

## Квоти, помилки та перевірка завтра

Перед запитом використовується існуючий атомарний `reserveLlmCall` з purpose
`tts_batch_lab`. Сімейство моделі визначає наявний quota ledger; конфіг квот не
змінюється. За відсутності ключа, DB чи доступної квоти запиту не буде.
`attempt.json` створюється ексклюзивно; повтор у ту саму папку неможливий.
Таймаут 240 секунд не спричиняє повтор. Після таймауту не можна знати напевно,
чи Google завершив генерацію, тому спроба залишається врахованою.
За 429/5xx локальне резервування повертається за існуючою політикою проєкту.
Успішна генерація записує використання токенів у спільний ledger; це окремий
скрипт, тому in-memory статистика NestJS не використовується.

Оцінити: чи всі 6 текстів озвучено повністю; чи не прочитані теги; чи не
обрізані перші/останні склади; скільки ручних правок; тривалість, час запиту
та usage. Один вдалий пакет — лише перший результат, а не доказ надійності.

Офлайн-перевірки:

```sh
npm run build
node --require ./tests/no-network.cjs --test tests/tts-batch-lab.test.mjs
```
